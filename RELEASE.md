# keel 2.6.4 — 2026-11-17

The business requirements document (BRD) now says where each assumption comes from. In our 2.6.3 test, every remaining contradiction between the documents and the code came from the generated BRD stating code details nobody had decided, such as that names are stored trimmed, or that two features share one helper. Now each BRD assumption names its source: your answer in the interview, the decision record that settles it, or *unvalidated*. A code detail with no answer behind it goes in a decision record or the low-level design instead. Doc sync compares these statements with the code and records any difference next to the original text, which is never rewritten or removed. The merge step also updates every status line in one commit, then runs the drift check.

**What we measured (n=9, one task, one tested model).** Three runs of three sessions on our
inventory test task, with documents generated by 2.6.4. All code tests passed. No session had a
business-requirements or decision-record contradiction (in 2.6.3 those caused every failure), and
no session stalled or left a status line behind. Drift still failed in 4 of 9 sessions, short of
our bar of at most 1 in 9: stale lines in the AGENTS.md rules table, in the docs index, and in
plan details. Those are not covered by this release.

### Added
- **A Source column in the BRD Assumptions table** (new projects), and guidance that risk
  mitigations naming code structure cite their decision record.
- **`/keel check` accepts a merged phase whose open gates are deferred**, and reports two more
  kinds of drift: `status-lag`, a status line in `AGENTS.md` or `CLAUDE.md` still saying a phase is on its branch after the plan shows it merged, or a README
  still saying no phase is built; and
  `brd-unsourced`, an assumption with no source, in a BRD whose table has a Source column.

### Changed
- **Doc sync** compares BRD assumptions, risk mitigations and product acceptance notes that name
  code behaviour with the code. When the build differs it records it, in order of preference, as
  the decision record's build deviation, as "superseded by the build" after the original text, or
  as an open decision for you when you were the one who said it. No row is removed.
- **The merge step** of phase and change scripts makes all its status edits in one commit and
  runs `node .keel/check.mjs` afterwards. It also ticks the "doc-sync commit present" gate, which
  Verify cannot see yet, and marks the phase done. Any gate still open becomes a deferred item, so
  a merged phase never leaves the next session told to "close" it first.
- **Exit gates** must be checkable in the project's own environment; a run on another runtime
  version or service is written as a CI or deploy gate, or deferred.

**Beyond the BRD change.** Our first 2.6.4 test run found that a phase could merge while still
marked unfinished, which stopped the next session. Three build-process fixes were added to this
release for that; none shortens a record document:
1. the merge step ticks the doc-sync gate, marks the phase done and turns any open gate into a
   deferred item;
2. exit gates must be checkable in the project's own environment;
3. `/keel check` `status-lag` also covers a README that still says no phase is built.

### Upgrading
- `/keel upgrade` offers the Source column for an existing BRD, with sources proposed from the
  interview transcript and *unvalidated* where none applies. It is applied only with your
  approval; the assumption text is not changed.
